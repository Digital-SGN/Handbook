# Соглашение о коммитах

Хорошая история коммитов — это не роскошь, а необходимость. Когда через полгода нужно понять, «почему этот код так написан» или «когда сломалось», именно коммиты дают ответ. **Conventional Commits** (Общепринятые коммиты) — простое соглашение о том, как писать сообщения так, чтобы история была читаемой и пригодной для автоматизации.

## Зачем это нужно

В любой команде рано или поздно возникает проблема: как понять, что изменилось между версиями? Что исправлено, что добавлено, что сломано? Если коммиты написаны как попало — `fix`, `update`, `правки`, `WIP` — ответа не найти.

Conventional Commits решает три задачи одновременно:

- **Читаемая история.** По коммиту сразу видно, что он делает и зачем.
- **Автоматизация.** Утилиты генерируют CHANGELOG, определяют следующую версию, запускают сборку — всё из истории коммитов.
- **Общий язык.** Одинаковые правила во всех проектах — не нужно каждый раз договариваться заново.

## Структура сообщения

Сообщение коммита состоит из трёх частей:

```text
тип(область)!: краткое описание

тело

подвал
```

- **Тип** — что делает коммит: `feat`, `fix`, `docs` и т.д. Обязателен.
- **Область** — необязательный уточняющий контекст в круглых скобках: `feat(parser):`.
- **`!`** — необязательный маркер ломающего изменения сразу после типа или области: `feat!:` или `feat(api)!:`.
- **Краткое описание** — сжатая формулировка изменения. Обязательно.
- **Тело** — подробности, если нужно. Отделяется пустой строкой.
- **Подвал** — ссылки на issues, `BREAKING CHANGE:` и другая мета-информация. Отделяется пустой строкой.

**Обязательны** только тип и краткое описание. Всё остальное — опционально.

## Типы коммитов

Основные типы определены спецификацией:

| Тип | Что означает |
| :--- | :--- |
| **`feat`** | Новая функциональность |
| **`fix`** | Исправление бага |

Дополнительные типы **не входят** в спецификацию, но широко используются на практике:

| Тип | Что означает |
| :--- | :--- |
| `docs` | Изменения в документации |
| `style` | Форматирование, отступы, пропущенные точки с запятой (не влияет на код) |
| `refactor` | Рефакторинг без новой функциональности и без исправлений |
| `perf` | Улучшение производительности |
| `test` | Добавление или исправление тестов |
| `chore` | Обслуживание проекта: сборка, зависимости, конфиги |
| `ci` | Настройка CI/CD |
| `build` | Изменения в системе сборки |

> **Про `improvement`.** Некоторые команды добавляют свой тип `improvement` — для улучшений без новой функциональности. Спецификация это разрешает: любой тип, кроме `feat` и `fix`, — на усмотрение команды.

## Область (scope)

Область уточняет, **какую часть** кодовой базы затронул коммит. Пишется в круглых скобках после типа:

```text
feat(parser): add ability to parse arrays
fix(auth): correct token expiration check
docs(readme): update installation instructions
```

Область **необязательна**, но полезна в больших проектах. Она позволяет понять, что именно изменилось, ещё до того, как вы откроете diff.

## Тело и подвал

**Тело** идёт через **пустую строку** после краткого описания. Здесь можно объяснить **почему** сделано изменение — то, чего не видно в коде.

```text
fix: prevent racing of requests

Introduce a request id and a reference to latest request.
Dismiss incoming responses other than from latest request.

Remove timeouts which were used to mitigate the racing issue
but are obsolete now.
```

**Подвал** идёт через пустую строку после тела. Здесь размещают:

- ссылки на issues: `Fixes #13`, `Closes #42`;
- `BREAKING CHANGE:`;
- информацию о соавторах: `Co-authored-by: Name <email>`;
- другие метаданные.

```text
fix: minor typos in code

See the issue for details on the typos fixed.

Fixes #12
```

## BREAKING CHANGE

**Ломающие изменения** — это изменения, которые нарушают обратную совместимость: код, работавший со старой версией, перестанет работать с новой. Их **обязательно** помечать.

Есть два равнозначных способа:

1. **Маркер `!`** сразу после типа или области — короткий и заметный вариант:

   ```text
   feat!: drop support for Node 14
   feat(api)!: remove deprecated endpoint
   ```

2. **`BREAKING CHANGE:`** (заглавными буквами, двоеточие, пробел) в начале **тела** или **подвала** — позволяет добавить пояснение:

   ```text
   feat: allow provided config object to extend other configs

   BREAKING CHANGE: `extends` key in config file is now used for extending other config files
   ```

Можно использовать оба способа одновременно: `!` для заметности, `BREAKING CHANGE:` — для пояснения.

`BREAKING CHANGE` может быть частью коммита **любого типа** — не только `feat` и `fix`. Например, рефакторинг может сломать API.

## Язык и стиль описания

- **Единый язык** во всём проекте: либо везде русский, либо везде английский. Смешивать не стоит.
- **Императивное наклонение** в кратком описании: `add`, `fix`, `remove`, `update`, а не `added`, `fixed`, `removed`. Так описание читается как команда: «этот коммит добавляет…».
- **Регистр** — любой, но **единый** во всём проекте. Если начали с маленькой буквы — продолжайте так.
- **Без точки** в конце краткого описания.
- **Один коммит — одно логическое изменение.** Если изменений несколько и они разного типа — разбейте на несколько коммитов.

## Примеры

Коммит без тела — только тип и описание:

```text
docs: correct spelling of CHANGELOG
```

Коммит с областью:

```text
feat(lang): add polish language
```

Коммит с телом и ссылкой на issue:

```text
fix: minor typos in code

See the issue for details on the typos fixed.

Fixes #12
```

Коммит с `BREAKING CHANGE` в теле:

```text
feat: allow provided config object to extend other configs

BREAKING CHANGE: `extends` key in config file is now used for extending other config files
```

Коммит с маркером `!`:

```text
feat(api)!: remove deprecated endpoint
```

Коммит без типа — **так делать не надо**, это пример несоответствия соглашению:

```text
Fix broken link in README
```

Правильный вариант того же изменения:

```text
docs: fix broken link in README
```

## Связь с SemVer

Conventional Commits напрямую связаны с **семантическим версионированием** (SemVer). Версия состоит из трёх чисел: `MAJOR.MINOR.PATCH`.

| Тип коммита | Версия |
| :--- | :--- |
| `fix` | **PATCH** — `1.0.0 → 1.0.1` |
| `feat` | **MINOR** — `1.0.0 → 1.1.0` |
| `BREAKING CHANGE` (или `!`) | **MAJOR** — `1.0.0 → 2.0.0` |

Это значит, что инструменты вроде `standard-version` или `semantic-release` могут **автоматически** определить следующую версию, посмотрев на коммиты с прошлого релиза. И заодно сгенерировать CHANGELOG.

Минимальный набор для старта: `commitlint` + `husky`. Этого достаточно, чтобы формат соблюдался без ручных напоминаний.

## Итог

- **Conventional Commits** — простое соглашение о структуре сообщений коммитов.
- Формат: `тип(область)!: описание`, опционально — тело и подвал.
- Основные типы: **`feat`** и **`fix`**.
- Дополнительные: `docs`, `style`, `refactor`, `perf`, `test`, `chore`, `ci`, `build`.
- **Область** в скобках уточняет контекст: `fix(auth):`.
- Ломающие изменения: **`!`** и/или **`BREAKING CHANGE:`**.
- Связь с **SemVer**: `fix` → PATCH, `feat` → MINOR, ломающее → MAJOR.
- Позволяет **автоматически** генерировать CHANGELOG и определять версию.
- Пишите коммиты так, как будто ваш код **уже используют другие**.
