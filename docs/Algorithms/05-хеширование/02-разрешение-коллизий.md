# Разрешение коллизий

В предыдущей главе мы научились превращать ключ в число. Казалось бы,
всё: считаем хеш, идём в ячейку, кладём значение. Но есть проблема,
о которой мы честно предупредили: **коллизии неизбежны.**

Ячеек `m`, ключей — сколько угодно. По принципу Дирихле, если ключей
больше, чем ячеек, хотя бы двое попадут в одну. А на практике —
и при меньшем числе, потому что хеш не идеален.

Значит, нужен способ разрешать коллизии. Их два больших семейства:
**цепочки** и **открытая адресация**. Разберём оба, посмотрим, где какой
используют, и в конце — про то, когда таблица должна расти.

---

## Способ 1: метод цепочек

Самая простая идея: в каждой ячейке храним **список** элементов,
которые сюда попали.

```
индекс 0: [ ]
индекс 1: [ ("alice", 30) ]
индекс 2: [ ("bob", 25), ("carol", 41), ("dave", 19) ]
индекс 3: [ ]
```

`put("carol", 41)`:
1. Считаем `hash("carol") % m` — пусть 2.
2. Идём в ячейку 2, добавляем в список.

`get("carol")`:
1. Считаем `hash("carol") % m` — тот же 2.
2. Идём в ячейку 2, **перебираем список** и ищем `"carol"`.

Всё. Никаких трюков.

```c
typedef struct Node {
    char *key;
    int value;
    struct Node *next;
} Node;

typedef struct {
    Node **buckets;   // массив указателей на головы списков
    size_t size;      // сколько элементов сейчас
    size_t capacity;  // сколько ячеек (m)
} HashMap;

void put(HashMap *map, const char *key, int value) {
    size_t idx = hash_string(key, map->capacity);
    for (Node *n = map->buckets[idx]; n; n = n->next) {
        if (strcmp(n->key, key) == 0) {
            n->value = value;   // ключ уже есть — обновляем
            return;
        }
    }
    Node *n = malloc(sizeof(Node));
    n->key = strdup(key);
    n->value = value;
    n->next = map->buckets[idx];
    map->buckets[idx] = n;
    map->size++;
}
```

> **Важно:** при `get` мы сравниваем **ключи через `strcmp`**, а не только
> хеши. Совпадение хешей — это ещё не совпадение ключей. Это и есть
> смысл разрешения коллизий: различать разные ключи с одинаковым хешем.

### Плюсы и минусы цепочек

**Плюсы:**
- Просто реализовать.
- Таблица не «забивается» — можно хранить больше элементов, чем ячеек.
- Удаление тривиально (убрать из списка).
- Load factor может быть > 1.

**Минусы:**
- Каждый элемент — отдельная аллокация (`malloc`). Плохо для кеша.
- Указатели `next` — это +8 байт на элемент минимум.
- При плохом хеше списки вырождаются в длинные цепочки → `O(n)`.

Именно цепочки используются в **Java `HashMap`** (до Java 8 — чистые
списки; с Java 8 длинные цепочки превращаются в красно-чёрные деревья,
если их длина ≥ 8, — это защита от hash-flooding).

## Способ 2: открытая адресация

Идея: **никаких списков**. Все элементы лежат прямо в массиве ячеек.
Если ячейка занята — ищем следующую свободную по какому-то правилу.

```
индекс 0: [ ]
индекс 1: [ ("alice", 30) ]
индекс 2: [ ("bob", 25) ]      ← сюда попал bob
индекс 3: [ ("carol", 41) ]    ← а сюда carol, потому что 2 была занята
индекс 4: [ ]
```

`put("carol", 41)`:
1. `hash("carol") % m = 2`.
2. Ячейка 2 занята (`bob`) → смотрим 3.
3. Ячейка 3 свободна → кладём.

`get("carol")`:
1. `hash("carol") % m = 2`.
2. В ячейке 2 лежит `bob`, не `carol` → идём дальше по тому же правилу.
3. В ячейке 3 — `carol`. Нашли.

Правило «куда идти дальше» называется **пробинг** (probing).
Самые популярные варианты:

| Метод                 | Шаг                              | Плюсы / минусы                          |
|-----------------------|----------------------------------|------------------------------------------|
| Линейное пробирование | +1, +2, +3, ...                  | Просто, кеш-дружелюбно, но кластеризуется |
| Квадратичное          | +1, +4, +9, +16, ...             | Меньше кластеров, но может не найти место |
| Двойное хеширование   | шаг = `hash2(key)`, зависит от ключа | Лучшее распределение, дороже считать  |

### Линейное пробирование

```c
void put(HashMap *map, const char *key, int value) {
    size_t idx = hash_string(key, map->capacity);
    for (size_t i = 0; i < map->capacity; i++) {
        size_t j = (idx + i) % map->capacity;
        if (map->buckets[j].state == EMPTY) {
            map->buckets[j].key = strdup(key);
            map->buckets[j].value = value;
            map->buckets[j].state = OCCUPIED;
            map->size++;
            return;
        }
        if (map->buckets[j].state == OCCUPIED &&
            strcmp(map->buckets[j].key, key) == 0) {
            map->buckets[j].value = value;
            return;
        }
    }
    // таблица полна — нужен рехешинг (см. ниже)
}
```

Заметьте: ячейка теперь имеет три состояния — `EMPTY`, `OCCUPIED`, `DELETED`.
Зачем `DELETED` — объясню ниже, это важно.

### Проблема кластеризации

При линейном пробировании занятые ячейки слипаются в длинные блоки
(«кластеры»). Чем больше кластер, тем вероятнее, что новый ключ попадёт
в него и увеличит ещё сильнее. Это как пробка на шоссе: одна авария —
и через минуту стоят все.

Двойное хеширование решает это: шаг зависит от ключа, поэтому разные
ключи «разбегаются» по таблице.

```c
size_t step = 1 + hash_string(key, map->capacity - 1);  // шаг != 0
size_t j = (idx + i * step) % map->capacity;
```

### Удаление и метка DELETED

Вот ловушка, на которой спотыкаются все. Представьте:

- `put("a", ...)` → попал в ячейку 5.
- `put("b", ...)` → хеш тоже 5, занято, попал в 6.
- `remove("a")` → ячейка 5 «освободилась».

Теперь `get("b")`: хеш 5, ячейка 5 **пустая** → алгоритм говорит
«ключа нет», и мы теряем `b`.

Поэтому «удалённая» ячейка — это не `EMPTY`, а `DELETED`: «здесь когда-то
что-то было, при поиске — продолжай, при вставке — можешь занять».

> **Важно:** без метки `DELETED` открытая адресация ломается на первом же
> удалении. Это не оптимизация — это необходимость.

### Плюсы и минусы открытой адресации

**Плюсы:**
- Всё в одном массиве → отличная локальность кеша.
- Нет `malloc` на каждый элемент.
- Меньше памяти (нет указателей `next`).

**Минусы:**
- Load factor не может быть > 1 (иначе некуда вставлять).
- Удаление требует метки `DELETED`.
- При высоком load factor деградирует быстро (при 0.9 линейное
  пробирование становится очень медленным).
- Плохо переносит плохие хеш-функции.

Открытая адресация используется в **Python `dict`** (комбинированная схема
с рандомизированным пробингом), **Rust `HashMap`** (по умолчанию — SwissTable
с открытой адресацией), **Go `map`** (частично).

## Сравнение

| Критерий              | Цепочки                  | Открытая адресация        |
|-----------------------|--------------------------|---------------------------|
| Локальность кеша      | Плохая                   | Отличная                  |
| Память на элемент     | +указатель + аллокация   | Только пара ключ/значение |
| Load factor > 1       | Можно                    | Нельзя                    |
| Удаление              | Просто                   | Нужна метка `DELETED`     |
| Деградация при плохом хеше | Плавная             | Резкая                    |
| Типичное применение   | Java, старые C++ STL     | Python, Rust, Go, C++ abseil |

> **Главная мысль:** нет «лучшего» метода. Есть «под задачу».
> Нужна максимальная скорость на средних данных — открытая адресация.
> Нужна предсказуемость и простота — цепочки.

## Load factor и рехеширование

Есть число, которое определяет, когда таблица «устала»:

```
load factor = size / capacity
```

- Для цепочек норм до ~0.75–1.0.
- Для открытой адресации — до ~0.7 (у Python — 2/3, у Rust — 7/8
  c SwissTable, но это уже тонкости).

Когда load factor превышает порог, таблица **расширяется**: создаётся
новый массив ячеек в 2 раза больше, все элементы **перехешируются**
(у них меняется `m` в `hash % m`, поэтому индексы пересчитываются).

```c
void resize(HashMap *map) {
    size_t new_cap = map->capacity * 2;
    Node **old = map->buckets;
    size_t old_cap = map->capacity;

    map->buckets = calloc(new_cap, sizeof(Node*));
    map->capacity = new_cap;
    map->size = 0;

    for (size_t i = 0; i < old_cap; i++) {
        for (Node *n = old[i]; n; ) {
            Node *next = n->next;
            put(map, n->key, n->value);  // перехешируем
            free(n->key);
            free(n);
            n = next;
        }
    }
    free(old);
}
```

Рехеширование — это `O(n)`, но происходит редко (амортизированно — `O(1)`
на вставку). Ровно та же идея, что у `std::vector` / динамического массива.

> **Важно:** при рехешировании **нельзя** просто скопировать элементы
> по старым индексам. `m` изменилось → все индексы другие. Каждый элемент
> должен пройти через хеш-функцию заново.

---

## А что в реальных языках?

- **Python `dict`** — открытая адресация, рандомизированный пробинг,
  resize при load factor 2/3. С версии 3.6 — упорядоченный (это следствие
  устройства, а не гарантия языка до 3.7).
- **Java `HashMap`** — цепочки, resize при load factor 0.75, длинные
  цепочки (≥ 8) превращаются в дерево.
- **C++ `std::unordered_map`** — цепочки (обычно), load factor 1.0.
- **Rust `HashMap`** — открытая адресация (SwissTable), load factor 7/8.
- **Go `map`** — открытая адресация с бакетами по 8 элементов.

Если вам нужна хеш-таблица в реальном коде — **берите стандартную**.
Свою пишите один раз, для учёбы, и больше не пишите.

---

## Итог

- Коллизии неизбежны, потому что ключей бесконечно много, а ячеек — `m`.
- Два способа: **цепочки** (список в каждой ячейке) и **открытая адресация**
  (ищем следующую свободную ячейку по правилу пробинга).
- Цепочки проще, но хуже по кешу и памяти. Открытая адресация быстрее,
  но требует метки `DELETED` и не любит load factor > 0.7.
- Load factor = `size / capacity`. При превышении порога — **рехеширование**
  в массив в 2 раза больше.
- При рехешировании **все** элементы пересчитывают индекс — `m` изменилось.
- В реальном коде используйте стандартные `HashMap` / `dict` / `unordered_map`.
  Своя реализация — это учебное упражнение, а не продакшн.
